The core write-safety design is sound:

- Writes are never retried. Only GET, HEAD and OPTIONS retry.
- CSRF is fetched before a mutation.
- Reviewed writes check the hash, then check and persist the journal, then send once.
- `--expect-plan` is enforced after `freshen`.
- Read-only mode is enforced like Python's.

Items 1 and 2 are the only safety holes I found, and Python has the same
holes.

### Error type size (P3)

I measured the types in a scratch crate:

| type | size |
|---|---|
| `serde_json::Value` | 72 B |
| `ApiError` | 128 B |
| `fsv_core::Error` | 128 B |
| `Result<Value>` | 128 B |
| `fsv_forms::FormError` | 192 B |

`#![allow(clippy::result_large_err)]` is in nine crate roots. **Fix:** change

## 2. Write safety

Verified:

- **No mutation retry.** `fsv-core/src/client/mod.rs:330-388` retries only when `should_retry` (`:937-945`) sees an idempotent method: `GET`, `HEAD` or `OPTIONS`, as in Python `client.py:29-32, 144-149`. `fetch_raw` (`:406`) never retries. `int_request` (`:673-692`) fetches CSRF first and sends once. A 403 triggers only a GET probe (`:418-441`). Redirect following is off by default (`:58`), so a POST is never re-sent to a 307 target. No crate above fsv-core has a retry loop. The "again/retry" grep hits are all refusal messages.
- **Journal.** `Client::request` (`:473-499`) journals every non-GET/HEAD call with the same status fallback as Python `_request`. The `Body::Raw` sends (reviewed writes, incident create) journal `plan_hash: null`, as Python's `content=` does. `classify` (`fsv-core/src/journal.rs:158`) mirrors `_classify`, including Unicode `\d` and `match` vs `fullmatch`.
- **Reviewed writes.** `fsv-api/src/reviewed_write.rs:64-135` follows `reviewed_write.execute` step by step: hash and tenant check, last-event check, `rebuild` hash, CSRF, `started` plus a readback that it was persisted, `send_once`, then `definite_rejection` to choose `failed` or unknown. `notes`, `tasks`, `approvals`, `associations`, `properties`, `conversations` and `catalog` follow the same pattern (`last_event … != Some("started")` after `record_plan("started")`).
- **Expect-plan.** `fsv-cli/src/cmd/changes.rs:1339-1395` calls `check_duplicate` → `freshen` → re-check → `expect` → `execute`, in Python's `_send` order (`change_cli.py:168-189`).
- **Read-only mode.** The TUI resolves the flag plus `tui.read_only` (`fsv-tui/src/actions.rs:14`) and gates the same entry points as Python: 54 checks in `app.rs`, 14 in `app/reviewed.rs`, against 59 in Python `tui/app.py`. These CLI commands refuse before sending, as Python does: `--read-only` on tasks-add, the approval commands, associations and add-note (`cmd/tickets.rs:307, 408`, `cmd/review.rs:43, 126, 248`, `cmd/links.rs:1011, 1054`). The hard-coded `read_only: false` at `cmd/tickets.rs:452` sits after the guard at `:408`, so it is correct.

### P0-1: Change create/update journals `failed` on ambiguous errors

`fsv-flows/src/change.rs:1559-1575` records `failed` when the first step
fails with `Error::Api(_) | Error::Other(_) | Error::Session(_)`. That
includes HTTP 500, 502, 503, 504, 429 and a 403 on `POST /api/_/changes`.

`recent_plan` treats `failed` as "may be retried"
(`fsv-core/src/journal.rs:398`), so `check_duplicate` lets the same create
plan through. A 504 or 502 from the proxy after the server created the
change therefore becomes a silent duplicate on the next run.

Python has the same bug (`change_flow.py:637-640`). Every newer path uses
"definite rejection = 4xx other than 403/408/429":

- incident create (`fsv-flows/src/ticket.rs:349-362`)
- SR `place-request` (`fsv-api/src/catalog.rs:1644-1660`)
- `reviewed_write` (`fsv-api/src/reviewed_write.rs:110`)

**Fix:**

```rust
Err(e) => {
    if fsv_api::service::definite_rejection(&e).is_some() {
        journal.record_plan("failed", …, PlanRecord { error: true, .. });
    }
    // else leave `started`: the outcome is unknown and check_duplicate blocks a resend
```

- Make `definite_rejection` `pub`.
- In the before-create flow, keep `failed` for an upload failure: the change was not posted yet.
- Record the change in PARITY ("Python marks 5xx/429/403/session failures as failed; Rust leaves them unknown, so `--allow-duplicate` is needed to resend").
- Add a test with `Reply::Status(503)` on `POST changes`: the journal ends in `started` and a second `execute` exits 4.
- Report it upstream too.

### P0-2: No check that `started` was persisted before sending

`fsv-flows/src/change.rs:1533-1538` calls `record_plan("started", …)` and
sends without reading it back. `record_plan` never fails: it swallows I/O
errors (`journal.rs:388`). With a full disk or a read-only state directory,
a create goes out with no ambiguity record.

Incident create checks (`ticket.rs:333-343`, "could not persist the
incident journal; nothing was sent"), and so do all the reviewed writes.

**Fix:** after `record_plan("started")`, require that the last
`plan:<action>` event for the hash is `started`, otherwise
`return Err(flow_exit(5, "could not persist the change journal; nothing was sent"))`.
The same applies to `catalog.rs:1601` for the upload-then-place flow, which
already does this. Record it in PARITY as a divergence (Python sends
anyway).

### P2: Read-only is enforced only in the UI

Python and Rust both gate read-only in key handlers and continuation
callbacks. These `Backend` write methods do not take `read_only`:

> `update_item`, `add_note`, `add_reply`, `send_association`,
> `update_task`, `delete_task`, `send_ticket_property`,
> `send_known_error`, `send_planning_text`, `send_ticket_conversation`,
> `open_form` (forms submit)

(`fsv-tui/src/backend.rs:433-603`). One missed `if self.read_only` in a new
flow would then write. **Fix:** in `fsv_app::run_tui`
(`fsv-app/src/tui.rs:1475`), when read-only resolves true, wrap
`LiveBackend` in a `ReadOnly<B>` that returns
`Failure("read-only mode: …")` from every write method and
`forms_available() = false`. This has no user-visible difference and costs
about 60 lines.

These are fine, but correct the record:

- **`Client::send_once` with no `Content-Type` on a bodiless request (`PARITY.md:146`).** This matches Python: `reviewed_write.py:65-68` adds `Content-Type` only with a payload, and `_int_request` always adds it, as Rust's `int_request` does. It is parity, not a divergence. Move it out of Divergences so a reviewer does not think a header changed.
- **`FSV_COMPLETION_NETWORK=1` "is a new env switch" (`PARITY.md:246`).** False. Python `completion.py:36` reads it. Delete the line.
- **"TUI workers do not drop stale generations" (`PARITY.md:37-39`).** This contradicts `ARCHITECTURE.md:86-88`. In practice Rust keeps Python's own guards (`pending_detail_key`, `list_epoch`, search seq; `fsv-tui/src/app/list.rs:55-80`, `app/detail.rs:25`), so the user-visible risk is the same as Python with `exclusive=True` workers. Make the docs agree: either implement the `(gen, Result)` drop in `spawn`, or edit ARCHITECTURE to "Python's staleness guards only".

Regressions to fix:

- **P1: YAML `true:` key (`PARITY.md:42-44`).** The claim that the loader "cannot tell a bool key from a quoted one" is wrong. `resolve_scalar` (`fsv-core/src/yaml.rs:94-100`) returns `Value::Bool` only for a *plain* scalar, and a quoted `"true"` arrives as `Value::String`. Python `yamlio.loads` returns `{True: '1'}` for `true: 1`, `{'true': '1'}` for `"true": 1`, and `{None: …}` for `null:` / `~:`. Rust's `key_text` (`yaml.rs:105-113`) maps them to `"true"` and `"null"`, which matches neither `str(k)` (`"True"`, `"None"`) nor what `json.dumps` would write for a typed key (`"true"`, `"null"`) at the call sites that `str()` the key. **Fix:** `key_text` returns `fsv_py::py_str(v)` for Bool and Null, as ARCHITECTURE item 8 already specifies ("typed keys stringified with `fsv_py::py_str`"). Audit the few call sites that `json.dumps` a loaded mapping without `str(k)` and give them a typed-key path if any exist. Drop the remap in the fsv-flows golden test.
- **P1: "Form review rows can show lookup ids where Python shows names" (`PARITY.md:93`).** This is user-visible review output, which is what users approve. `fsv_flows::meta::ClientResolver::name_for` (`meta.rs:366`) exists now. Wire it into the review row rendering, then remove the line or add a golden.
- **P1: `SendFailure::into_error` exit code for an `Exit` cause (`PARITY.md:145`).** Python's `exit_code_for` gives 1; Rust uses the cause's code. This is not one of the README-table fixes. Either match Python (1) or show the README row that justifies the change.
- **P2: `conversations::parseaddr` is simplified (`PARITY.md:143`).** Recipient emails go into the conversation plan payload and therefore its hash. For `"Doe, John" <j@x>` both give `j@x`, but quoted local parts and comments differ, which changes payload and hash. Because this is wire-relevant, port `email.utils.parseaddr` exactly (about 150 lines of `_parseaddr.AddrlistClass`), or reject inputs outside the supported subset with a usage error so the user never gets a different payload.
- **P3: cookie with and without `Domain` is one cookie (`PARITY.md:199`).** This changes the `Cookie` header bytes (Python sends both). It is acceptable, because it is safer and the server takes the first. Tag it "wire: Cookie header" so the end reviewer sees it.

Stale ledger entries that read as gaps but are not:

- `PARITY.md:94` says properties are not loaded. `fsv-app/src/tui/tests_actions.rs:805` tests that they are.
- `PARITY.md:97` says "Not yet wired in LiveBackend: change tasks …". All 58 `Backend` methods are implemented (`fsv-app/src/tui.rs:598`).
- `PARITY.md:137` says `07c85d0` canned is not ported. `fsv-api/src/canned.rs` exists, but the CLI does not (see section 6).
- `PARITY.md:280-281` says "fsv-flows meta partial / no live client yet". `fsv-app/src/writer.rs` is the live client.

**Fix for the ledger:** add a `last-verified: <rust sha> / <python sha>`
line to every crate section in `port/parity/*.md`. Have one reviewer pass
delete every claim a test contradicts.

No divergence I sampled changes a plan hash, journal kind, cache filename,
session byte or draft key, except the YAML key case and the `parseaddr`
edge cases above.

## 5. Coverage audit

I re-ran it with `--no-cargo --out /tmp/... --json /tmp/...`. Result: 1431
covered, 56 fn-only, 22 missing, 147 n/a. The committed `COVERAGE.md` says
1286 / 119 / 135 / 85 and that the script lives in `/tmp`, so it is stale.
Breaking down the 1431 covered rows:

- **1204 are "test ref".** `tested()` (`fsv_coverage.py:611-625`) counts a fn as tested when any test text anywhere contains its name. For uncommon names this is checked across all crates. 82 covered rows cite evidence in a crate that cannot depend on the fn's crate. Examples:
  - `change_flow._encode` → evidence `fsv-core/src/session/tests.rs`
  - `cli._client` → `fsv-api/src/watchers.rs`
  - `canned.content` → `fsv-forms/src/py_golden.rs`

  Most of these do have some valid reference elsewhere; only one, `client._query_string`, has none. But the evidence column is misleading, and the matcher pairs functions wrongly: `change_cli._pick` → `fsv-formui/src/widgets/combo.rs:235`, `cli._api` → `fsv-app/src/tui.rs:352`.
- **130 are credited through a "Port of" doc comment.** `port_idx` (`:680-686`) takes every dotted token after "port of" on the line, and that credit wins over name matching. One sloppy doc line can credit several Python functions.
- **68 are "golden binary run".** `reached_golden` (`:657-677`) walks a name-regex call graph up to 6 hops from a dispatch target that some golden argv runs. That is static reachability, not execution. For example, `cli._setup_network_completion` is credited through `setup`, but the golden `setup` run may exit before that branch.
- **29 are "argv".** The doc admits these "may only reach argument validation".

The audit is useful as an inventory ("is there a Rust fn for every Python
def?"). It does not show that behavior is tested against Python.

**Fix (P2):**

1. Scope `tested()` to the fn's crate and the crates that depend on it, and require an `fsv_x::` / `crate::` path or a `use` that resolves to the fn's module.
2. Replace reachability with execution. Run `cargo llvm-cov --workspace --json` once and mark a fn "executed" when its body has at least one covered line. Keep "golden" only for fns executed by a test whose file includes a committed golden (`include_str!(…golden…|…oracle…|…fixtures…)`).
3. Report three columns instead of one "covered": `has-fn`, `executed-by-test`, `executed-by-golden`.
4. Make the `COVERAGE.md` header name `port/fsv_coverage.py` and the Python and Rust commits it ran against.

## 6. Upstream drift

Current state:

- The Python repo had about 50 commits in the last 7 hours (≈8.5 minutes apart).
- `UPSTREAM.md` last triaged `dbe553c`. 5 commits are untriaged: `10c3281`, `ed6e644`, `44e3e83`, `820af12`, `92002d7`, all about planning and problems verification.
- 27 Python command paths have no Rust counterpart. Several of them write (`problems write-child`, `tickets private-views write`, `tickets scenarios apply`, `tickets canned reply`, `* columns set`):

  > `changes asset-picker`, `{changes,problems,tickets} columns {list,set}`, `{changes,problems,tickets} export`, `problems create`, `problems write-child`, `tickets canned {folders,list,reply,show}`, `tickets private-views {show,write}`, `tickets scenarios {apply,list,show}`

- `tests/tree.rs` compares against the checked-in `cli_tree.json`, not live Python, so the gap is invisible to `cargo test`.
- `generated.rs` says it is "@generated by tests/golden/gen_tree.py", but that script is missing and the file was hand-edited after generation (`PARITY.md:241`).

Recommended process: a batch cycle, not commit-chasing.

1. **Pin the reference.** Keep `port/UPSTREAM_BASE` holding one Python SHA. Every golden generator runs against `git worktree add /tmp/fsv-py-<sha> <sha>`, never the live main worktree. `ARCHITECTURE.md:3-6` currently says to include uncommitted files, which is not reproducible.
2. **`port/sync.py` (new), run hourly or every 10 commits:**
   - `git log BASE..HEAD --name-only` appends a stub row per commit to `UPSTREAM.md` with status `untriaged` and the touched Python modules mapped to crates. Reuse `prefs()` from `fsv_coverage.py`.
   - Re-dump `cli_tree.json` and `completion_tree.json` with `dump_cli_tree.py` / `dump_completion.py` at the new SHA and diff them. New or removed commands, options or help text are listed as failing items.
   - Re-run every `port/golden/gen_*.py` and `crates/*/tests/golden/gen_*.py` at the new SHA into a scratch dir and diff against the committed fixtures. Each changed fixture names the Rust tests that must be re-checked. With the commit header from section 4 this is mechanical.
   - Run `fsv_coverage.py --no-cargo` at the new SHA. New Python defs with no Rust fn are listed per crate.
   - Map new or changed Python test files (`tests/test_*.py`) to the crate that owns the module, as "tests to port".
3. **CI gate.** Make `cargo test -p fsv --test tree` fail when `cli_tree.json`'s `_python.commit` is older than `UPSTREAM_BASE`. That forces the tree to be re-dumped when the base moves.
4. **Restore `gen_tree.py`.** Fold the hand edits (module name, doc comments, hint fixes) into the generator. Otherwise each upstream CLI change means hand-merging 6.6k lines.
5. **Triage rules.** Advance `UPSTREAM_BASE` only when every row is `ported`, `partial` with a named follow-up, or `wontfix` with a PARITY entry. Give commits touching `client.py`, `journal.py`, `reviewed_write.py`, `safety.py`, `*_flow.py` or `catalog.py` a "write-safety" tag that blocks the base move until they are ported.
6. **One owner per crate** for each batch, as `UPSTREAM.md:565` already suggests. Collapsing the duplicate modules from section 1 roughly halves the number of places an upstream fix must land (formmeta: 2 → 1, recipients: 4 → 1).
