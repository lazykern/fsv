# Freshservice forms, field metadata and business rules

**What this is.** How Freshservice describes its forms (ticket, service
request, problem, change, task and catalog-item forms), what each field
type looks like on the wire, which flags make a field required, and how the
client-side **business rules** change what the agent web UI shows and
accepts. It explains why a client that writes records must evaluate those
rules itself.

**Who it is for.** Developers of `fsv` or any other client that fills
Freshservice forms outside the browser. For the `fsv` implementation of the
rules engine and the `br_validation_excludes` token, see
[the form engine page](../forms.md); this page is the platform behaviour
behind it.

**Verified on:** a Freshservice Enterprise trial tenant, 2026-11-11 to
2026-11-13, plus read-only metadata reads of a production-like enterprise
tenant. Field names, labels and ids below are invented examples.

**Confidence tags:** **[VERIFIED LIVE]** sent and read back;
**[CAPTURED]** request shape seen, not executed live; **[INFERRED]**
reasoned from metadata, code or UI. *Read-only* means a GET on a
production-like tenant.

## 1. Where form metadata comes from

| Form | Metadata endpoint | Envelope key |
|---|---|---|
| Ticket (incident and service request share it) | `GET /api/_/ws/<ws>/ticket_form_fields` or `GET /api/_/ticket_form_fields` | `ticket_fields` |
| Change | `GET /api/_/change_form_fields` (optionally `?workspace_id=<ws>`) | `change_fields` |
| Problem | `GET /api/_/problem_form_fields` or `GET /api/_/ws/<ws>/problem_form_fields` | `problem_fields` |
| Release | `GET /api/_/release_form_fields` | `release_fields` |
| Tasks | `GET /api/_/ticket_task_fields`, `/change_task_fields`, `/problem_task_fields`, `/release_task_fields` | `<module>_task_fields` |
| Catalog item | `GET /api/_/catalog/service-items/<display id>` | `service_item` (fields under the item, grouped in sections) |
| Existing requested item | `GET /api/_/tickets/<id>/requested_items/<item row id>?view=more_info` | `requested_item` with the item's field definitions, plus `business_rules.hidden_req_item_fields` and `non_editable_item_fields` |
| Business rules | `GET /api/_/ws/<ws>/business_rules?ember_api=true&module_type=<m>&form_type=new_form\|edit_form&...` | `business_rules` + `user` |

All [VERIFIED LIVE]. Which path answers (workspace-scoped or plain) differs by
tenant and module, so try the workspace path first and fall back.
[VERIFIED LIVE]

There is **no per-field operator metadata** for list filters: filter
operators are built into the web app (see
[wire contracts, filters](wire-contracts.md#filters)). [VERIFIED LIVE]

## 2. Field shape

A form field, as returned by the metadata endpoints (values invented):

```json
{
  "id": 501, "name": "region", "label": "Region", "field_type": "custom_dropdown",
  "required": false, "required_for_closure": true, "position": 12,
  "default_field": false, "workspace_id": 2,
  "choices": [{"id": 701, "display_id": 31, "value": "North", "label": "North"}],
  "nested_fields": [], "lookup_config": null, "data_source": 0,
  "displayed_to_agents": true, "placeholder": "", "helptext": "Where it happened"
}
```

* `name` is the API key. Custom fields go under `custom_fields` in payloads
  and appear as `customFields.<name>` in business rules (`customField.<name>`
  in catalog-item rules). Default fields (`priority`, `group`, `agent`,
  `category`, ...) are top-level and have their own payload keys
  (`group_id`, `responder_id` on tickets, `agent_id` on changes and problems).
  [VERIFIED LIVE]
* Field names for custom fields are generated by the platform from the label
  at creation time; labels without Latin letters produce opaque generated
  names (for example `rand<digits>`), and some types get a type prefix
  (lookup fields, multi-select fields). Never derive a name from a label;
  read it. [INFERRED]
* `position` is the order of the form, which is also the order in which a
  person filling the form top to bottom triggers rules. [VERIFIED LIVE]
* Change custom planning sections are fields of type `planning_field`
  (custom ones are named with a `cfp_` prefix, for example
  `cfp_go_live_checklist`); they are written through the planning-fields
  endpoints, not through `custom_fields`. [VERIFIED LIVE]

### Field types

Default (built-in) types seen: `default_requester`, `default_subject`,
`default_description`, `default_status`, `default_priority`,
`default_urgency`, `default_impact`, `default_risk`, `default_source`,
`default_ticket_type`, `default_category`, `default_group`, `default_agent`,
`default_department`, `default_change_type`, `default_change_reason`,
`default_change_impact`, `default_change_plan`, `default_backout_plan`,
`default_change_window`, `default_planned_start_date`,
`default_planned_end_date`, `default_planned_effort`,
`default_release_type`. [VERIFIED LIVE, read-only]

Custom types seen: `custom_text`, `custom_paragraph`, `custom_number`,
`custom_checkbox`, `custom_date`, `custom_dropdown`,
`custom_multi_select_dropdown`, `nested_field`, `custom_lookup`,
`custom_multi_lookup`, `custom_content` (static text, no value),
`custom_attachment` (catalog file fields), `planning_field`.
[VERIFIED LIVE, read-only]

| Type | Wire value in `custom_fields` | Readback | Notes |
|---|---|---|---|
| `custom_text`, `custom_paragraph` | string | string | Not filterable in lists. [VERIFIED LIVE] |
| `custom_number` | number (sent as written) | may come back as a string | Compare numerically. [VERIFIED LIVE] |
| `custom_checkbox` | `true` / `false` | boolean | [VERIFIED LIVE] |
| `custom_date` | ISO 8601 with the account offset; catalog date fields `YYYY-MM-DD` | same | The UI shows `DD-MM-YYYY` and converts. [VERIFIED LIVE] |
| `custom_dropdown` | the choice **value (label)** | label | Filters also use the label. [VERIFIED LIVE] |
| `custom_multi_select_dropdown` | list of labels | list | Filters use the **integer choice id**, not the label. [VERIFIED LIVE] |
| `nested_field` | top level under the field name, lower levels under their own `nested_fields` names, each as a label | same | See below. [VERIFIED LIVE] |
| `custom_lookup` | the looked-up record id | `{id, value}` object | Values come from a lookup endpoint. [VERIFIED LIVE] |
| `custom_attachment` (catalog) | list of uploaded attachment ids | list of file objects | Upload first. [VERIFIED LIVE] |

### Choices

* Default fields: `{"id": 2, "value": "Open"}`; status choices also carry
  `internal_id`, SLA-timer flags and a customer-facing label. **Write the
  `id`, never `internal_id`.** [VERIFIED LIVE]
* Custom choices: `{"id", "display_id", "value", "label"}`. Business-rule
  `populate` actions refer to choices by **display id**. [VERIFIED LIVE]
* Task metadata serialises choice ids as **strings** (`"1"`, `"900"`); the
  server accepts integers on write. [VERIFIED LIVE]
* Status, task status, reminder and approval-related choice lists are
  tenant-configurable: the same label can have different ids on two
  tenants, and ids can be renumbered after admin edits. Resolve by label
  from fresh metadata every time. [VERIFIED LIVE]

### Nested (dependent) fields

* A `nested_field` holds a tree: each choice has `nested_options` for the
  next level, and the field lists its lower levels in `nested_fields`
  (each with its own `name` and `label`). The default `category` field works
  the same way with `sub_category` and `item_category`. [VERIFIED LIVE]
* A lower level is only valid when its parent value is set and the value is
  a child of that parent. The UI clears lower levels when the parent changes.
  [VERIFIED LIVE]
* When a rule hides a nested field, its lower levels are hidden with it.
  [VERIFIED LIVE]

### Lookups

* `custom_lookup` fields carry `lookup_config: {"data_source": <n>, "link":
  "/lookup_choices?field_name=<name>_<account id>&module=<module>"}`; the
  client calls that link with `q=<text>` and stores the returned record id.
  [VERIFIED LIVE]
* People pickers use autocomplete endpoints:
  `GET /api/_/search/autocomplete/requesters?q=<text>&qf=details` (labels
  `Name <email>`, returns user ids) and
  `GET /api/_/search/autocomplete/agents?q=<text>&qf=name`. The agent
  autocomplete can put the email in `id` and the assignable identity in
  `user_id`; match on the field you need. [VERIFIED LIVE]
* Catalog-item lookup fields exist as separate types; their submission shape
  was not proven. [INFERRED]

## 3. Required flags

| Flag | Where | Meaning |
|---|---|---|
| `required` | form field | required for agents on create/edit. [VERIFIED LIVE] |
| a separate customer-side required flag | form field | required on the self-service portal; agent writes do not use it. [VERIFIED LIVE, read-only; exact key name not recorded] |
| `required_for_closure` | form field (boolean) | required when moving to a closed/resolved status. [VERIFIED LIVE] |
| `field_options.required_for_create` / `field_options.required_for_closure` | task fields, catalog-item fields | the same idea, but nested in `field_options` and often a **string** `"true"` / `"false"`. Accept both boolean and string. [VERIFIED LIVE] |
| other `field_options` strings | catalog-item fields | `requester_can_edit`, `displayed_to_requester`, `visible_in_agent_portal`, `is_sensitive`, `max_attachment_limit` (`"1"`), `allowed_file_types` (a JSON list in a string), `date_only`. [VERIFIED LIVE] |

Rules on requiredness:

* The flags are the **static** requiredness. Business rules make fields
  required or optional on top (`mandate` / `unmandate`). [VERIFIED LIVE]
* Closure requirements apply only to fields that are **visible** after the
  rules run: a closure-required field hidden by a rule is not demanded by
  the UI. [VERIFIED LIVE]
* Some requirements live only in the UI. Examples: a task's planned effort
  must look like `1h 30m` (the UI rejects `01:30` before sending); the
  maintenance-window form refuses an empty condition row although the API
  accepts empty criteria; the 40 MB upload limit is a UI label and the
  server accepted a larger file. [VERIFIED LIVE]
* The server enforces its own checks too: missing required fields answer
  HTTP 400 with per-field errors; problems have **closure rules**
  (`violated_closure_rules`, for example "analysis completed" and
  "workaround or solution added") that are not readable as metadata and only
  show up as a 400. [VERIFIED LIVE]
* Tenant custom fields can be required where the platform default is
  optional, including on tasks (a task form can require a custom field the
  stock form does not have). Read `required_for_create`. [VERIFIED LIVE]

## 4. Business rules (client-side form rules)

Business rules are configured per module (and per catalog item) by admins
and executed **in the browser**. The server only learns the outcome through
the request body and the `br_validation_excludes` token.

### Fetching

`GET /api/_/ws/<ws>/business_rules` with `ember_api=true`, `module_type`
(`ticket`, `change`, `problem`, `release`, `service_request`), `item_id`
(catalog item internal id or `null`), `form_type` (`new_form`, `edit_form`),
`module_id` (the record on an edit form), `user_type`, `requester`,
`requested_for`, `include_workspace`, `filter_by_default_form_action` and
`cf_name_prefix`. The server filters the rules for that context, so fetch
them the way the web does for the form you are filling. [VERIFIED LIVE]

Two response shapes [VERIFIED LIVE]:

* `{"business_rules": [...], "user": {...}}`: the evaluable form shape.
  `user` is the signed-in agent's profile that `current_user` conditions
  read.
* `{"business_rule": [...]}`: an admin listing with positions but **no**
  conditions or actions. It cannot be evaluated.

On some tenants one module's rule endpoint answers **HTTP 500** for every
agent variant while other modules work. Treat that as "rules unavailable",
not as "no rules". [VERIFIED LIVE, read-only]

### Rule shape

```json
{
  "id": 3001, "name": "Region North needs a site", "module_type": "ticket",
  "workspace_id": 2, "item_id": null, "form_type": "both", "user_type": "agent",
  "state": "active", "rule_type": "client_side", "deleted": false,
  "is_reversible": true, "is_validation": false,
  "condition_data": {"all": [
    {"name": "customFields.region", "operator": "is", "value": "North", "evaluate_on": "ticket"}
  ]},
  "action_data": {"action": [
    {"property": "show", "name": ["customFields.site"]},
    {"property": "mandate", "name": ["customFields.site"]},
    {"property": "populate", "name": ["customFields.site"], "values": [41, 42]}
  ]}
}
```

* `condition_data` is `{"all": [...]}` or `{"any": [...]}`; items are
  conditions or nested groups. `{"all": null}` means unconditional.
  [VERIFIED LIVE]
* Operators: `is`, `is_not`, `includes`, `does_not_include`, `selected`,
  `not_selected`. Values are compared against a choice's value, label, id
  or display id. [VERIFIED LIVE]
* The same rule id can appear twice in one response (a reversible and a
  non-reversible entry with different action lists); both are applied in
  order. [VERIFIED LIVE]
* `form_type` is `new_form`, `edit_form` or `both`; `user_type` is `agent`,
  `requester` or `both`. [VERIFIED LIVE]

### `evaluate_on`: what a condition reads

| `evaluate_on` | Reads |
|---|---|
| the module name (`ticket`, `change`, `problem`, `service_request`, `form`) | the live form answers. [VERIFIED LIVE] |
| `current_user` | the signed-in agent (groups, department, ...) from the `user` object. [VERIFIED LIVE] |
| `requester`, `requested_for` | the selected requester / beneficiary record. [VERIFIED LIVE] |
| `system` | the form context, for example `portal` (agent UI vs self-service portal). [VERIFIED LIVE] |
| `current_entity` | on an **edit** form, the saved record as loaded, not the live answers. Can reference record attributes that are not form fields. [VERIFIED LIVE, read-only rule sets; evaluated offline] |

### Actions

| `property` | When matching | Reverse (reversible rule not matching) |
|---|---|---|
| `show` / `hide` | show / hide the targets | hide / show |
| `mandate` / `unmandate` | required / not required | the opposite |
| `disable` / `enable` | read-only / editable | the opposite |
| `populate` | **restrict** a dropdown's choices to the listed display ids; it does not set a value | full list again |
| `message` | show a message; blocks submit when the rule `is_validation` | message removed |

All [VERIFIED LIVE] against captured web behaviour.

### Rules that hide page parts, not fields

Action targets are not always form fields. Rules can hide or require parts
of the page [VERIFIED LIVE, read-only rule sets]:

| Target | Page part | Payload keys that carry it |
|---|---|---|
| `tags` | the Tags control | `tags` |
| `approval_request` | the "Request approval" control | approvals |
| `config_item_ids` | "Associate CIs" on create | `device_ids`, asset ids |
| `add_child_ticket` | the child-ticket control | child tickets |
| `add_service_item`, `edit_service_item` | requested-item add/edit | requested items |
| `attachment_ids` | general request attachments on a catalog form | `attachments` |

A client that would send one of these keys while a rule hides the control is
doing something the web UI cannot do. [INFERRED]

## 5. How rules change what the UI shows

* On load the web evaluates every rule in array order against the load
  values (defaults on a new form, the record on an edit form); reversible
  rules that do not match apply their reverse. [VERIFIED LIVE]
* Every user change re-evaluates the rules in array order. A typical
  enterprise tenant uses a discriminator dropdown (for example a field named
  Ticket Kind) whose value shows one block of fields and hides the others,
  mandates a few, and restricts the choices of dependent dropdowns.
  [VERIFIED LIVE]
* The visible required set at closure can be much smaller than the set of
  fields flagged `required_for_closure`, because the rules hide most of
  them for a given discriminator value. [VERIFIED LIVE]
* `populate` restricts choices but leaves the value alone, so a stale value
  outside the restricted list stays until the user changes it. [VERIFIED LIVE]
* `message` rules with `is_validation: true` block submit until resolved.
  [VERIFIED LIVE]

## 6. Why a writing client must evaluate the rules

1. **The server does not re-run client-side rules.** It applies its static
   required checks, skipping the ones listed in `br_validation_excludes`.
   The web always sends that token on creates and on most property updates
   and transitions. A client that omits it hits static required checks the
   UI would have relaxed; a client that forges it can bypass requirements.
   [VERIFIED LIVE / INFERRED]
2. **Hidden fields must not be sent.** The UI never submits a hidden field;
   a write that does produces a record no agent could have produced.
   Refuse, never drop silently. [VERIFIED LIVE]
3. **Rule-mandated fields are only enforced in the browser.** Without
   evaluation, a client can create records that the UI would have blocked.
   [INFERRED]
4. **Edit forms differ from new forms.** Edit-form rules (often with
   `current_entity` conditions) govern updates, status changes and closure.
   Fetch them with `form_type=edit_form` and the record id. [VERIFIED LIVE]
5. **When rules cannot be fetched or evaluated, fail closed** for writes the
   unknown rules could govern, and say why. Computing the wrong required set
   silently is worse than refusing. [INFERRED]

`fsv` implements this in `fsv.forms` (rules engine, payload builders and the
token builder); see [the form engine page](../forms.md).

## 7. Tenant differences to expect

* Catalog items each have their own rules (`item_id`); many items have none.
  [VERIFIED LIVE]
* A trial tenant often has almost no rules; a production-like tenant's
  incident form can be entirely rule-driven. Test rules on a tenant that has
  a realistic rule set (see [live testing](../live-testing.md)).
  [VERIFIED LIVE]
* Field metadata can be at parity between tenants while rules, lifecycles
  and workflows are not; compare all three. [VERIFIED LIVE]
